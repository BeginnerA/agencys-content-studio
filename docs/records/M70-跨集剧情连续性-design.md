# M70 跨集剧情连续性设计

> 归档戳：2026-10-29，设计决策稿；对话中的三部分方案已确认，本文待用户书面审阅，尚未开始实施。
> 授权边界：本轮仅整理本设计并自审；不改业务代码、总路线图或其他里程碑，不提交或推送 Git，不调用真实付费模型。M68 数字人口播继续暂缓。

## 1. 目标与已确认决策

让连载短剧从“带上上一集文本”升级为“引用有来源、有人确认、可追溯的此前剧情”，减少人物状态、角色认知、道具归属和伏笔的跨集断裂。首版交付可验证的连续性管理闭环，不宣称能发现所有语义矛盾或保证模型绝不剧透。

用户已依次确认：

1. 提升重点为跨集剧情连续性；采用“结构化剧情台账 + 按集人工确认 + 续集承接”，而非只加长摘要或建设完整叙事知识图谱。
2. AI 从明确选定的剧本版本整理每集变化，逐条编辑、排除后一次确认整集；未确认草稿不生效。剧本 gate 批准不等于剧情台账批准。
3. 分开记录已经发生的事实、角色认知和创作计划；“观众知道甲是卧底”不等于“乙知道甲是卧底”。
4. 新增一张通用内容连续性登记表，正文复用文本资产与不可变内容版本；不重建角色库、剧集库或记忆系统。
5. 开启连续性承接后，生成前预览此前有效已确认记录，实际使用的输入包冻结留档；前集改变后标记待复核，显示实际引用影响，不自动改写后集。
6. UI 放入现有剧集地图；手动运行、智能创作、工作流使用同一服务端校验。未开启时保持原流程。
7. 开发验收先使用离线三集夹具及隔离浏览器样例；真实模型效果另行授权、单独报告。

### 1.1 非目标

不新增短剧执行引擎、完整知识图谱、自动整剧重写、自动付费纠错、平行时间线推理或新供应商通道；不修改 M68、M69、旧自动摘要的无关问题；不把四级滚动摘要升级为事实真源。不为历史运行伪造它们从未记录过的输入证据。

## 3. 系统边界与模块分工

新增 `services/continuity/` 作为通用内容连续性服务，内部按职责拆分：契约与归一化、来源解析、台账读写、提取、有效性/影响计算、承接包、调用证据。每个模块单一职责，单文件不超过仓库 800 行红线。

通用层处理有序内容单元、版本、人工确认、依赖和承接；首版适配器把 `series` 映射为集合、`episode` 映射为单元。不新增体裁专用引擎，不以模型输出决定项目归属、集号、批准状态或可消费性。

数据流：

`明确剧本版本 → AI 提取/人工复核草稿 → 整集确认 → 有效性计算 → 第 N 集承接预览 → 用户确认冻结 → queued 前绑定 → ai_text 调用前复核与注入 → 调用证据/输出版本 → 后续影响查询`

台账确认、承接确认、制作确认是不同动作；界面可以合并后两个确认按钮，但服务端必须保留各自的哈希与条件检查。没有任何 AI 回复、自动摘要、步骤完成事件可以代替人工确认。

## 4. 持久化契约：一张登记表，正文一个真源

### 4.1 通用登记表

新增 `content_continuity_records` 一张表。使用 `rowType=entry|context|consumption` 区分本集台账、冻结承接包和一次模型调用证据；三者共享归属、文档版本、幂等与状态登记机制，不再增设台账明细表、上下文表或调用任务表。

核心字段：

- `id, projectId, scopeKind, scopeId, unitKind, unitId, unitOrdinal`：首版 kind 分别为 series/episode，ID 与集号由服务端从现存归属解析，禁止客户端任意拼接。
- `rowType, status, revision`：生命周期与 CAS 版本；revision 是登记行的并发令牌，不是正文版本号。
- `documentAssetId, documentVersionId, documentHash`：唯一正文指针及完整性哈希。正文只存于通用文本资产/不可变版本，不在表中再存一份事实 JSON。
- `sourceRunId, sourceStepId, sourceAssetId, sourceVersionId, sourceHash`：entry 的来源定位索引；完整来源凭据在正文内，二者必须一致。
- `runId, stepId, parentId`：context 绑定的运行、consumption 绑定的步骤与父 context；entry 的 `parentId` 表示所克隆的旧登记（无则空）。
- `operationKey, requestHash, approvalKey, approvalHash, replacedById, errorCode, createdAt, updatedAt, confirmedAt`：幂等、确认、替代与状态元数据；approvalHash 绑定用户审阅的正文、来源、依赖、被替代头版本与缺口接受列表，不重复存正文。错误仅存脱敏摘要；不存凭证或完整模型请求到日志。

数据库约束：

1. `(projectId,rowType,operationKey)` 唯一；相同键、相同请求返回同一操作，相同键、不同 requestHash 返回冲突。确认使用独立 approvalKey/hash，不能把提取请求的幂等键当成确认凭证。
2. entry 在同一 `(projectId,scopeKind,scopeId,unitKind,unitId)` 下最多一行 `status=confirmed`，用部分唯一索引保障，不仅靠进程锁。
3. context 只可绑定一次运行；CAS 在创建该 run 的同一事务完成。consumption 的 operationKey 由服务端的 run/step/执行轮次确定，客户端不能造键绕过去重。
4. 文档持久化、登记指针和状态发布必须同事务可见；使用外层事务的服务必须通过同一个 executor 读写，不能在事务里盲用全局 db。

### 4.2 文本资产和版本

新增保留 purpose：`continuity_entry`、`continuity_context`、`continuity_use`，格式均为经专用 schema 校验的 JSON。生成用正文为其中可复现的渲染结果，渲染器版本写入快照。

文件使用带随机标识的独立名称，写入后创建 `content_versions`，再发布登记指针。复用 `writeTextAsset`、`recordAssetTextVersion` 的能力，但不假定它们已一起完成原子发布。文件先于数据库产生的孤儿不允许被查询为有效件；失败只清理本次未发布文件，不删除别人的共享资产。

草稿每次保存生成新不可变版本并 CAS 更新指针；确认只冻结当前已经审阅的版本。确认后修改须克隆新 entry，不能覆盖原版本。通用内容编辑、版本恢复、替换上传等所有可改变这些保留 purpose 的入口必须拒绝写入，不能只靠前端禁用。普通剧本的既有编辑方式不变。

登记用资产不挂在某个源 run 的批量清理归属下；run/step 关系记在登记表与正文。这样删除源 run 不会顺带销毁本来用于说明失效原因的台账。归属项目彻底删除时仍一起清理。

## 5. 本集台账正文与确定性累计

### 5.1 正文结构

`ContinuityEntryV1` 包含 `schemaVersion=1`、集合/单元身份、来源凭据、基础依赖 `basis`、主题与主体字典、`items` 和待审的完整性提示。确认摘要/时间另记登记行，不在点击确认后悄悄改写已经审阅的正文版本。批准人身份仅使用现有应用真实可提供的身份；没有用户身份系统时只记录确认时间和操作键，不编造账号。

主体优先引用已有实体 ID；无实体时使用本剧范围稳定的本地 key 和显示名，不自动创建角色。别名合并、人物同一性由人确认，不凭同名猜测。AI 可提议复用 topicKey，服务端校验该 key 和前序条目确实存在。

每条 item 的必需语义：

| 字段 | 规则 |
| --- | --- |
| `id, topicKey` | 服务端分配稳定条目 ID；topicKey 代表一个可跨集承接的主题或状态槽 |
| `channel` | `fact` 已发生事实、`knowledge` 特定主体认知、`plan` 创作计划，不能混用 |
| `type` | `event` 事件、`state` 状态、`relationship` 关系、`possession` 道具归属、`thread` 伏笔 |
| `operation` | `set` 新增/替换、`close` 明确结束/回收、`retract` 撤销不可信记录；撤销不恢复更旧值 |
| `subjects, value` | 主体 key 数组与简洁陈述；事实值不是自动执行指令 |
| `knower, epistemic` | knowledge 必填，认知为 `knows|believes|unaware|unknown`；其他 channel 不填 |
| `previous` | 更新已有主题时引用确切 entry/version/item；新主题为空，禁止悬空或跨剧引用 |
| `evidence` | 原文定位数组 `{start,end,quote}`；索引以 JS UTF-16、左闭右开计，quote 必须等于选定版本的 slice |
| `origin, editNote, included` | `extracted|manual|edited`，人工新增/改写须说明，排除条目留在草稿历史但不累计 |

`unaware` 必须有原文明示或明确人工补充依据；“未写到他知道”只能是不确定，不能自动生成“不知道”。观众作为独立认知主体，不把观众信息复制给角色。计划条目默认不进入下一集的正式事实区，可在预览中单独勾选“编剧参考”，并继续使用醒目标签。

原文子串校验只能证明引用确实存在，不能证明模型解释正确。因此所有提取项仍须人工整集确认；修改了 AI 结论即标 `edited`，不能继续展示为“未经修改的原文事实”。

### 5.2 合并与冲突

按叙事集号升序、同集条目顺序折叠，不用故事内日期重新排序。同一主题的 fact、knowledge（再按 knower 区分）、plan 分别维护；不同 channel 不互相覆盖。

更新当前值必须准确指向该主题的有效前值。不同分支同时替换、重复当前值、无前值却声称回收、前值失效等情况列为结构冲突，禁止确认，要求人工修正；不以“最后一条赢”掩盖冲突。追加事件使用独立 topicKey，不覆盖过去事件。close 保留回收依据，retract 表示当前值不可信且不回退旧值。

每集可确认一个空变化清单，但必须明确勾选“本集无新增变化”；这和“没有记录”不同。首版不推断未记录的世界状态，不负责平行世界、跨分支和复杂倒叙的自动一致性计算。

### 5.3 基础依赖

`basis` 保存本次提取/复核实际读过的已确认 entry/version/hash，以及来源剧本生成时已记录的连续性依赖；来源未知的历史生成明确标 `history_unavailable`，不伪造已知依赖。

用于模型提取的基础包全量作为依赖记录，而非仅记录模型最后提到的条目；人工补充的 previous 引用也必须加入。人工复核若不再依赖某项，必须明确解除并说明，服务端校验没有悬空引用，不提供自动“全部解除失效”按钮。

## 6. 来源选择、有效性与版本变动

### 6.1 唯一来源定位

来源凭据包含 project/series/episode、集号、run ID、模板快照哈希、step ID/key、资产 ID、contentVersion ID、原文 UTF-8 sha256，以及选定时的步骤输出资产集合和 gate 状态指纹。

服务端检查：所有对象同项目、同集；run 的模板快照及 `episode_number` 与集一致；step 属于 run；资产属于该 step 且为未删除文本。候选列表必须显示步骤标题、真实 key、运行、版本、批准/未批准状态，不只显示文件名。续跑继承的成功产物定位到实际产生它的原 run/step，并显示继承关系，不把新 step ID 伪装成产物来源；原对象不可达时按来源缺失处理。

新模板在目标步骤的开放 params 中声明 `continuity_role: episode_script`。首版为 `mengbao-episode.write_script` 增加声明；历史快照只为该确切 templateKey/stepKey 提供窄兼容映射。其他旧模板可人工明确指定已有输出步骤，但需在界面显示“未声明剧本角色”，不可自动选择 `script_review` 或任意 purpose=script。

确认台账时，来源必须仍是该步骤当前输出资产之一，步骤已 succeeded；有 gate 者须 `decision=approve`，skip/reject 不视作批准。历史版本可以查看、提取为草稿，但若不是当前字节则不可直接确认为当前事实；须先经现有方式使其成为当前剧本，再重新绑定复核。

新生成资产可能还没有内容版本。GET 来源列表仅展示“尚未捕获版本”，不在查询中隐式补写；用户选定后通过专门 snapshot POST 校验 run/step/asset 和所见原文哈希，捕获 baseline 并返回可选 versionId。这个动作不调用模型、不代替 gate 或台账确认；承接 preview 仍保持纯只读。

读取当前字节、计算 sha256、检查版本实际内容三者必须一致。不能因 `ensureAssetTextBaseline` 返回已有 revision 就假定版本与文件相同；发现“文件已变但版本未成功登记”时提示来源漂移，不用旧版本名掩盖新字节。

### 6.2 什么会使已确认记录待复核

entry 的生命周期与有效性分离：`confirmed` 表示曾人工确认；`valid|stale|missing|corrupt` 是按当前依据计算的有效性。只有 confirmed 且 valid 可以进入正式承接。

历史追溯完整性另记 `known|history_unavailable`，不与有效性混为一谈。旧运行没有生成快照不代表当前剧本已失效；用户仍可审阅当前原文并确认台账，但该缺证提示必须进入确认摘要和后续承接缺口列表，显式接受才能使用。此许可不能用于掩盖已知的版本漂移或消费结果不明。

以下事件使对应记录不再默认可信：来源文件/哈希/版本改变，当前步骤输出替换、退回或撤销批准，来源对象被删除或归属改变；被引用的前序 entry 失效或被另一确认版本替代；正文或版本文件缺失、哈希不符。

新建另一 run、更新 episodes.latestRunId 或开始新的提取，本身不替换当前确认来源，不自动使旧确认版失效。用户确认新 entry 时才在一个事务中将旧 confirmed 改 superseded，并发布新 confirmed。若旧来源本身早已改变，则旧记录本来就是 stale，提取失败不能把它恢复成 valid。

失效按实际依赖向更大集号传播，形成有向无环关系。它不是“前集变了所以全部后集都用过它”的推断；没有引用的后集不记为实际受影响。有历史追溯缺口则显示“无法确认是否引用”，不显示“零影响”。

有效性读取时重算并在确认、冻结、消费前强制复查。资产编辑/恢复、gate 变化等钩子只用于及时刷新提示，不作为唯一安全闸；即使通知丢失或服务重启也不能误放行。

## 7. 提取、编辑、确认与失败状态

### 7.1 操作契约

1. 用户选来源并点“AI 整理剧情记录”，看见可能调用模型、费用未知或估价、字符规模和所用基础包。服务端解析项目配置但不回传 API Key。
2. 请求显式带 `allowModelCall=true`、幂等键和来源/基础包预览哈希。来源、大小、schema 与 `checkBudget` 预检通过后，原子插入 entry/extracting 占位；重复请求返回同一登记，不新增调用。
3. 提取走既有 `chatCompleteDetailed` 和用量记录通道，一次逻辑请求，不做格式修复式自动二次调用。提示词把原文当资料，禁止原文中的指令控制流程；不开工具调用。
4. 成功则校验结构、证据及来源是否仍当前，持久化草稿；若提取期间漂移，草稿标待复核，可看但不能直接确认。失败记录错误，不动其他已确认版。
5. 草稿编辑携 `expectedRevision`，完整 schema 校验后写新文档版本。确认携登记 revision、documentVersion/hash、当前来源指纹、已展示警告哈希，以及用户所见的本集 `expectedCurrentConfirmedId`（首次为空）。再次计算依赖并比较当前头，在同一事务 CAS 确认并替换旧 confirmed。
6. 两个客户端即使确认的是不同草稿，只要基于同一个旧头版本，也只有一个成功；第二个得到 409，不悄悄覆盖。确认成功后再点同一 approvalKey/hash 返回同结果；不同内容不能复用操作键。

首版提取采用长请求，前端同时可用 GET 查询已占位操作；不新建后台任务引擎。客户端断连不等于请求未发出，重连按同幂等键查询，不主动重发模型请求。服务启动时只将本进程遗留 extracting 标 unknown，不自动付费恢复；实现限定与现有单服务进程部署口径一致，进程内互斥不是数据库唯一约束的替代。

### 7.2 状态与费用不确定性

entry 生命周期：`extracting → draft|failed|unknown`；`draft → confirmed`；被新确认替代为 `superseded`。stale 为有效性标记，不抹除曾批准的历史。

网络超时、连接中断、响应拿到但落盘失败可能已经产生费用，标 unknown 或附“费用结果不明”，不得写成“未扣费”。用户重试必须新操作键并再次明确同意；无自动付费重试。底层供应商/SDK 如有重试行为，实施时必须核对并为该路径禁用可导致重发生成请求的透明重试；做不到则停止启用而非承诺精确一次。

复核旧记录允许零模型费用：克隆草稿，绑定当前来源，重新核对证据、修改条目和依赖后人工确认；不强迫重新 AI 提取。若提取失败但来源与依赖没变，原有效确认版继续可用。

工程限制使用集中常量：原文最多 120,000 个 UTF-16 code unit、提取输入总计最多 160,000、单清单最多 200 条、单条 value 最多 1,000、单清单正文最多 200,000。超过直接返回可操作错误，首版不做静默分块/裁剪。输出 token 预算与这些输入字符上限分开配置；字符上限不等于供应商 token 窗口保证。

## 8. 第 N 集承接：预览、冻结、绑定与使用

### 8.1 预览内容

只收集同项目、同剧、集号严格小于 N 的当前 confirmed 且 valid 的记录；第 N 集自身、未来集、草稿、superseded、stale 均不进入正式事实区。第 1 集可产生显式空承接包。

包包含：

- 累计人物状态、关系、道具归属、角色/观众认知差异、未回收伏笔与已回收依据，均能反查 entry/version/item。
- 独立的可选编剧计划区（默认关闭），不标成已发生或角色已知。
- 缺集、失效、历史追溯不全的完整列表。第 1..N-1 集没有 confirmed 的就是缺口；不存在的集号也不得被忽略。
- 本次实际纳入的全部记录版本、依赖图、确定性渲染文本、渲染器版本与哈希。
- 目标 episode、templateKey、模板快照哈希、目标 stepKey、归一化制作输入哈希（排除随后生成的包 ID）、模型相关非秘密配置指纹。

预览只读，不自动生成摘要、不调用模型。缺口可以由用户明确接受后继续，但包必须保留接受的精确列表和理由，生成提示词仍标“未知，不能补成既定事实”。不能接受把 stale 当有效事实，也不能一键放行所有未来变化。

承接渲染默认上限 24,000 字符，模板可显式下调；首版不提供自动摘要或主题裁剪。超限必阻断，不能仅勾选“接受”绕过。用户可精简过长台账并重新确认，或明确关闭本次承接；不得把下游事实保留却悄悄删除其认知/伏笔依赖。另检查完整模型消息输入字符限额；仍不能承诺任意模型窗口都足够。

### 8.2 冻结与新运行

预览响应携 `previewHash`，覆盖目标、输入、配置指纹、有效记录全集、缺口和选项。确认请求携该哈希、接受缺口列表、includePlans 和幂等键；服务端重建预览并比较，发生变化即 409，不用用户没有看到的新包替代。

通过后创建 context/frozen 登记、专用资产与不可变版本。包 ID 只能由专用确认服务生成；普通上传一个同 purpose 的 JSON、LLM 决策中的资产 ID 或猜到历史包 ID 都不构成人工批准凭证。

正式模板输入为 `with_continuity`（bool，默认 false）及 `continuity_context`（files，可选但启用时必须恰好一个合法冻结包）。两者必须列入模板声明，不能依赖未声明字段透传；普通素材选择器不能充当包选择器。建 run 的守卫先检查原始连续性意图，再做模板归一化：不支持的模板收到启用请求必须拒绝，不能先丢弃字段后把它当未启用；关闭时携带包 ID 也视为矛盾输入。

创建 run 时在同一事务中复核包、插入 queued、把 context CAS 绑定该 run。相同确认的重复提交返回已绑定 run；同包试图创建另一个不同输入/目标 run 返回冲突。未绑定但来源已变的包需要重新预览确认，不更新原包正文。

有外层事务的智能创作沿用该事务；无外层事务的手动创建由服务包裹事务。需要读取和更新的 executor 类型随之显式扩展，不能只改签名为可写而实际另用全局连接。引擎只能在提交后启动，绝不先放出 queued 再补绑定。

### 8.3 模型调用前的统一闸门

仅声明 `continuity_role: episode_script` 的非 batch `ai_text` 步骤消费包；读取 run 模板快照与归一化 input，不从实时模板猜步骤。启用但没有合法声明、目标多个或目标为 batch 时明确 unsupported，不能忽略开关后继续收费。

目标步骤在发请求前复核：目标和绑定、输入与配置指纹、正文版本/哈希、当前来源与依赖、缺口接受范围、大小与预算。以本次将送出的文本构建完整消息，把连续性区放入明确分隔的事实/认知/可选计划区；不经过 `clipContent`，不让普通 files 循环再次读包资产并重复注入。

`setting_docs`、`brief`、`prev_script` 仍可用，但标为其他参考，不认证为台账事实。它们可能包含未来规划或用户明确改写要求；M70 只保证自动选取的正式承接不越集，并让来源可审，不保证外部文档无剧透或模型一定遵守。

源在排队期间变化则阻断并要求重新确认；源在最终复核之后或外部请求在途时变化，已发送的冻结字节不变，结果到达后标注“基于已变化依据”，不取消事实、不自动重投。安全边界是调用前复核时点，不宣称能原子锁住外部模型和所有文件系统操作。

## 9. 调用证据、恢复与影响追溯

### 9.1 不能把 prepared 等同已使用

consumption 登记在模型调用前创建，保存 context 版本、实际完整 messages（不含密钥）、消息哈希、准确来源版本、run/step、模型、开始时间。正文仍是 `continuity_use` 资产版本；状态转换每次先持久化可回看的证据，再发布指针。

状态为 `prepared → dispatching → completed|failed|unknown`：

- prepared 仅表示准备完成；未发出请求，不能标“模型已使用”。
- dispatching 在调用前 CAS，表示请求可能已发出；崩溃恢复按 unknown 处理，绝不仅因没有输出而自动重发。
- completed 只在收到响应、用量处理和输出资产/版本已持久化并建立关联后发布，表示应用确认该响应来自本次调用；不等于有供应商结算凭证。
- 明确的本地发出前失败记 failed 且 `submitted=false`。其他错误附提交/费用不确定标记；无法证明没发出时归 unknown。

重复执行相同 run/step 的已 completed 记录复用已持久输出，不再次调用。prepared 且能证明尚未开始 dispatch 的操作可恢复；dispatching/unknown 必须先人工核验，或用户明确同意可能重复费用后另建操作。输出已持久但步骤状态尚未更新时也优先复用；不得把“数据库未写 succeeded”当供应商失败。

M70 的准备证据写失败发生在调用前则阻断；响应后证据写失败不抹去可能已收费的事实，保留 unknown，禁止自动重试。旧 `safeRecordExecSnapshot` 仍为旁路，可额外用显式 versionId 写 `continuity_entry/context` 角色，不将它改成全仓硬失败机制。实际引用查询以 M70 登记为主，兼容旧快照并显示可信度。

### 9.2 断点续跑与重跑

普通 `/runs/:id/resume` 虽直接插表，也必须复用同一恢复服务：

- 已成功的目标剧本步骤被复制为终态时，不重发该步骤；保留旧调用证据链接，显示“继承已有输出”。后续台账依据仍来自实际原始生成。
- 目标步骤确需重跑时，旧 context 的一次绑定不可直接挪给新 run。先重新预览当前记录，显式确认并创建新包；校验通过才创建新 queued。
- 若此前为 dispatching/unknown，未核验或未明确再次费用确认不得建可重发运行；成功输出可复用时不得要求付费重做。
- 模板快照与恢复输入不匹配则阻断，不能静默换成最新版模板或自动关闭 with_continuity。未启用的旧 resume 不受此附加流程影响。

### 9.3 影响展示

查询同时展示：直接引用的提取、实际完成生成、可能发出但结果不明的请求，以及通过已确认台账传播的间接影响。区分“准备过”“完成并关联响应”“结果不明”“历史未记录”。每项带旧来源版本、当前差异、目标集/run/step、消费包与建议动作。

前集修改只改变当前有效性投影，历史包和历史生成输入不可改。后集稿件不自动覆写，运行不自动重启；用户可先零模型复核台账，再决定是否使用既有返修能力。改写不是确认新事实的替代，确认新事实也不是授权重新计费。

## 11. API 与前端契约

以下为拟新增路由，不代表现有 API 已提供；复用现有 Hono 错误包装和项目归属检查。

| 方法与相对路径 | 用途 |
| --- | --- |
| `GET /projects/:pid/episodes/:eid/continuity/sources` | 明确候选步骤产物、版本与当前可确认性；仅返回同项目同集 |
| `POST /projects/:pid/episodes/:eid/continuity/sources/snapshot` | 用户选定来源后捕获缺失 baseline，精确返回版本；免费且不作批准 |
| `GET /projects/:pid/episodes/:eid/continuity` | 当前登记、草稿/历史、有效性及缺口 |
| `POST /projects/:pid/episodes/:eid/continuity/extract` | 显式付费提取；幂等返回同一 operation/entry |
| `POST /projects/:pid/episodes/:eid/continuity/review` | 从现存登记克隆零模型复核草稿，重新绑定当前来源 |
| `PATCH /projects/:pid/continuity/:id` | 仅 entry/draft 的结构化编辑；必填 expectedRevision |
| `POST /projects/:pid/continuity/:id/confirm` | 比较正文、来源、依赖、警告哈希并整集确认 |
| `POST /projects/:pid/continuity/preview` | 只读构建目标集预览；POST 便于传完整待运行输入，不写资产 |
| `POST /projects/:pid/continuity/contexts` | 用户批准预览后冻结包；幂等，不发模型请求 |
| `GET /projects/:pid/continuity/:id/impact` | 区分直接、间接与未知引用影响 |

提取操作未完成时 GET 列表可查询其状态；不存在或跨项目的登记使用同一 404 面，避免越权泄露。不可接受的结构/大小返回 400/413，冲突/需复核/预算与需要重新确认返回 409，供应商调用失败按现有服务约定映射且保留操作 ID。

稳定业务错误码至少覆盖：`continuity_source_invalid`、`continuity_source_changed`、`continuity_conflict`、`continuity_evidence_invalid`、`continuity_dependency_invalid`、`continuity_gaps_unaccepted`、`continuity_context_too_large`、`continuity_context_changed`、`continuity_context_claimed`、`continuity_unsupported`、`continuity_outcome_unknown`。预算透传既有 code，不把所有冲突糊成 503。

前端在 SeriesBoard 增加“剧情记录”状态与入口，复杂内容拆到专用组件：

- 来源版本选择与可能费用提示；原文/条目并排，定位引文，显示人工新增、人工修改、排除和结构冲突。
- 草稿整集确认；无变化也能明确确认；当前有效、待复核、未记录三态不可只用颜色区分。
- 启动页承接预览显示人物状态、认知差异、伏笔、计划开关、缺口和费用边界；变更目标/输入后清除旧批准状态。
- 影响列表链接真实历史版本与运行，零模型复核与返修分开。请求中禁重复按钮，后端幂等仍为必需。

所有新 UI 使用现有交互与样式，不进行无关视觉重设计。M70 保留 purpose 在普通素材列表中默认不参与自动选材，不干扰现有“最新 text/script”等兜底读取。

## 12. 删除、清理与完整性

软删项目、源资产、运行或文件缺失时：读取历史登记仍可解释失效原因，新的确认/承接拒绝把不可达依据当有效。只有来源工作副本被删而不可变版本还在时，可查看历史版本，但仍不默认为当前事实。

同项目中的台账、上下文、调用证据及所引用不可变版本应纳入清理保护，既有自动版本回收不可删除被登记引用的版本。直接删除保留 purpose 资产应拒绝并引导使用项目级清理；不得让普通素材清理悄悄毁掉审阅历史。用户明确删除原始剧本或运行不被改写成“从未引用”，影响视图标来源缺失。

剧集缩容目前只检查 latestRunId/contentAssetId；新增检查该单元是否仍有 continuity 登记或被引用，有则拒绝缩容，不能在解除 latestRunId 后留下悬空归属。首版不新增随意移集/改集号 API。

项目彻底删除在 [routes/projects.ts](../../apps/server/src/routes/projects.ts) 的同一删除事务内清登记，再清通用资产/版本/追溯对象；正在 extracting/dispatching 的连续性操作也必须作为活动写入拦截。失败回滚不能留下半删除关系。磁盘清理沿用提交后 best-effort，不改变别的项目文件。

新增操作认领和项目删除须在同一写事务纪律下复查项目存在性/活动登记，避免“检查后新发起提取”的竞态；响应回写也要检查项目和原操作仍存在且状态可写，不能在已删除项目下重新插入资产。unknown 是历史未决结果，不自动恢复活跃写任务。

[session-delete.ts](../../apps/server/src/services/creation-chat/session-delete.ts) 的影子项目删除面也纳入同样登记/活动操作守卫；仅删除已立项会话不删除项目台账。M70 不允许向无有效剧集的影子项目创建台账，但清理防线仍需覆盖异常残留。

## 13. 验收与退出标准

### 13.1 离线三集主夹具

使用全新隔离临时目录与数据库，不读生产媒体，不接真实供应商。第 1 集：甲受伤、钥匙由甲持有、观众知道甲是卧底而乙不知，埋下红信封伏笔；第 2 集：钥匙交给乙、乙只怀疑甲身份，红信封未打开；第 3 集：红信封揭晓。未来计划另设“乙将发现身份”，不能提前写进第 2 集已知事实。

按顺序提取、编辑、确认第 1/2 集，准备第 3 集，随后改第 1 集。验证生成前拿到的具体文本与版本、认知与伏笔状态、实际影响名单；未被依赖的旁支运行不被伪称已引用。

### 13.2 必测矩阵

1. 来源：script_review 与 write_script 同 purpose 仍选对步骤；最新 run 不替代确认来源；错项目/错集/错步骤/软删/历史字节/缺失版本均被正确处理。
2. 事实：三个 channel 隔离，未提及不等于不知道；别名不自动合并；伏笔 close 与 retract 语义正确；previous 悬空/失效、结构冲突和伪造引文不能确认。
3. 人审：草稿/排除项不生效，人工新增/修改有标记；空清单确认不同于缺集；两个客户端竞争只有一个确认成功；源在提取或确认期间漂移不能误发布。
4. 幂等与费用：相同键不多调用，不同内容同键冲突；预算拦截零调用；超时/断连/重启/响应后落盘失败不自动重发；零模型复核路径确实零调用。
5. 承接：第 N 集排除 N 及未来、未确认和失效记录；完整缺口提示与精确接受绑定；plans 默认关闭；超限不截断；消息实际字节与冻结版本相同。
6. 漂移：预览后新确认了前集、修改来源、替换 gate 输出、改变模板/集号/待运行输入/模型配置，旧 preview/context 均不能静默继续；在途变动保留真实输入而提示结果依据已变。
7. 多入口：手动、route/template、route/chain、专业 workflow、autoAdvance 阻塞、普通 resume 逐个请求级测试；synth 无声明/batch 目标明确拒绝；旧 easy 与 with_continuity=false 不新增调用或数据写入。
8. 恢复/证据：queued 前已有完整绑定；包并发认领不双建；prepared 与 dispatching 不混淆；completed 输出可复用；继承成功步骤保留原证据；未知结果不伪装失败可重投。
9. 失效/清理：前序版本替代导致实际依赖待复核，无静默回退；缺历史显示未知；源删除、项目 purge、影子项目清理、剧集缩容、保留版本回收保护、事务失败均有断言。
10. 非回归：原 prev_script、滚动摘要、gate 执行、智能创作 decision/planHash、预算、未开启运行与现有通用快照旁路保持原行为。

测试注入假的 LLM 与用量返回、可控时钟及故障点，断言请求次数和持久证据，不仅断言 UI 文案。新增 `probe-m70` 覆盖本轮契约，并按仓库惯例纳入回归；计划阶段明确具体任务、测试文件与所有权，不在设计阶段执行。

### 13.3 浏览器与质量边界

隔离样例实际走通“提取草稿 → 修改/排除 → 整集确认 → 第 2/3 集承接预览 → 改前集 → 待复核与影响列表”，另验证缺口/超限/未知结果的禁用与恢复提示。检查小屏布局、键盘操作、错误信息和真实版本链接。不能把前端编译通过称为浏览器验收。

实施完成后运行该里程碑探针、相关旧探针及 `pnpm ci:check`，记录本次真实命令与结果，不引用 M69 的旧成绩代替。CI、离线契约、浏览器交互、真实模型质量分开报告。

真实模型质量验收需用户另行确认供应商、模型、测试素材与单次费用授权；届时比较人物状态承接、认知泄露、伏笔回收和人工修订量，并给出具体失败样例。不预设没有依据的准确率或节费百分比，模拟测试不能证明真实创作质量。

## 14. 风险与实施约束

- 自由文本仍存在解释歧义：用结构化来源、明确未知和人工确认降低风险，不把“有引用”包装成自动语义证明。
- 确认/调用是数据库与文件/供应商之间的跨边界操作：以 CAS、不可变文件、调用前证据和 unknown 恢复控制重复请求，不承诺供应商 exactly-once 或绝对不产生重复费用。
- 全集累计会增长：首版强上限、显式阻断，不引入第二套付费摘要；如后续确需压缩，另行设计可验证压缩与遗漏批准机制。
- 新增表承载三种登记而非三份正文真源：各 rowType 使用独立 schema/状态校验，避免任意状态组合；服务文件按职责拆分。
- 来源/追溯底层存在版本与工作副本不一致、旁路快照不完整的历史情况：新增路径严格识别，不顺手重构全仓 provenance 或资产编辑事务。
- 本稿不授权修复旧自动摘要查询、变更生产数据、安装依赖或联网真测。发现改变既有安全边界的必要调整，应在实施计划中显式列出并走批准门禁。
